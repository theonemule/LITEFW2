# LiteFW2 native nftables migration: safety and verification

**Status:** development branch only. This change has not been released, published,
deployed to a router, or used to cut over an active firewall.

## Separation of responsibilities

- **nftables** is the Linux kernel firewall / NAT policy engine. LiteFW owns
  only the native nftables table named inet litefw.
- **iproute2** continues to manage live interfaces, addresses, bridges,
  routes, default gateways, and policy routing. It was already in use.
- **OpenRC nftables** restores the native persistent ruleset from
  /etc/nftables.nft at boot. A destroy-table directive ensures that reloading
  only the LiteFW-owned table is idempotent and does not flush other tables.

The interface for web and CLI clients remains the same: ordered firewall
rules, port forwards, management services, staged Apply/Keep with a timeout
and rollback, and the local-console emergency bypass.


## One source-to-destination traffic policy

The Firewall page displays a **single ordered policy list** including WAN,
network segments/interfaces, and traffic originating on or destined to the
firewall host. **New rule** opens a guided editor: choose source, destination,
protocol, source/destination ports, and Allow, Block or Reject. Optional
source/destination address selectors accept IPv4, CIDR, inclusive IPv4 ranges,
or comma-separated address lists. TCP/UDP port selectors accept single ports,
inclusive ranges and lists.

For common needs, choose **Guided examples** (LAN to WAN, between segments,
blocking, firewall host access or publishing a service). The rules display as
readable sentences; native iptables/nftables commands are not exposed.

The user sees one global order with up/down priority controls. **First
matching rule wins in the applicable kernel packet path**: INPUT for traffic
to this firewall, OUTPUT for traffic generated by it, and FORWARD for traffic
passing through it. Moving an INPUT rule relative to an OUTPUT rule does not
cause those unrelated packets to traverse the other hook. Protected LAN-only
management web access and established-connection rules remain ahead of custom
traffic rules.

The **Published services** section configures destination NAT, not a separate
firewall filter policy. User forward-block rules are evaluated before the
automatic allowance for DNAT.

Rules remain staged locally until **Apply changes** and an explicit **Keep**
confirmation. Unconfirmed policy changes revert automatically within
120 seconds. Unmanaged native rules are displayed read-only and preserved
when staging. The console remains available for emergency recovery.

## Deliberately unsupported in-place conversion

Do **not** install this backend over a running LiteFW2 iptables installation.
Existing iptables rules may include imported nonstandard expressions, custom
forwarding, module hooks, and management access controls. Silently dropping any
of those is unsafe. The installation and runtime-only upgrade paths refuse a
legacy active ruleset instead of attempting an automatic conversion.

The original rules, network services, and management path must be exported and
reviewed first. A future console-controlled migration should translate all
active filter and NAT rules, verify the translated native nftables set in an
isolated network namespace, ensure recovery access and a boot-time fallback,
then switch the firewall only with explicit approval. Do not run iptables and
nftables simultaneously expecting that one will override the other: both
Netfilter hooks can be active.

Older LiteFWM installations with an existing inet litefwm table are also
protected against automatic takeover. An installation on a fresh Alpine
appliance may use the native nftables backend without a legacy migration.

## Validation for this source branch

Run syntax checks on scripts and parsers. Use a privileged **disposable**
Alpine 3.24 container for native-kernel integration checks:

~~~sh
sh -n lib/fw.sh lib/common.sh bin/litefw-recovery install.sh
awk -f lib/fwparse.awk </dev/null
sh tests/firewall-staged-apply.sh
sh tests/firewall-recovery.sh
sh tests/nft-module.sh
node tests/firewall-ui-model-test.js
# Browser integration: mock-firewall-ui-server.py and firewall-ui-browser-test.js
~~~

The tests cover native ruleset compilation; state readback; ordered user
rules; TCP and UDP DNAT; WAN masquerade; unmanaged rule retention; 120-second
configurable confirmation and timeout rollback; break-glass bypass and restore;
LAN-only management guard; native GeoIP interval sets; and preserving
unrelated nftables tables.

## Local ISO integration verification (November 14, 2026)

The release-candidate ISO was built locally on the isolated nftables branch,
not published. The exact locally tested artifact and checksums are documented
in `docs/LOCAL_ISO_QA.md`.

The **full three-stage KVM QEMU run passed** using `tools/test-iso-local.sh`:

1. Offline ISO boot, disk installation with no network interface, installed
   disk boot, and validation of the LiteFW runtime, services and console.
2. Live ISO with simulated WAN/LAN, real packet forwarding and masquerade,
   TCP DNAT, first-match blocking/allow recovery, WAN web denial, and
   authenticated UI/API create/edit/delete of structured host rules.
3. Reboot from the *installed disk* with the same WAN/LAN packet and API tests.

Disposable Alpine integrations passed 11/11: native nftables filter/NAT,
GeoIP interval sets, staged Apply/Confirm rollback, break-glass recovery,
VPNs including a WireGuard handshake, BGP, DNS, module contracts and
authentication. The local web wizard passed a headless Chromium interaction
smoke. The install+uninstall test for optional openNDS 11.0 and cloudflared
passed; openNDS 11.0 calls nftables, despite its legacy source filename.
The local overlay permission regression catches an apkovl root-directory
mode that otherwise prevents unprivileged daemons from starting.

**Remaining release/production gates:** no cutover or configuration migration
has been performed on a real firewall or existing iptables appliance;
that requires a separate, console-backed conversion plan and approval.
Dedicated hardware/network-driver verification and a captive-portal session
against actual guest clients have not been performed. The ISO remains a local
candidate, not a published GitHub release.
